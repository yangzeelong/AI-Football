# touch_eval — 触球判定与精度评估

用一条带人工标注的视频衡量「AI-Football SDK 能不能准确判断球员触球」。
SDK 保持通用（`sdk/aifootball/**` 未改动），判定与评估是它下游的业务逻辑：
**C++ 只跑基模（检测 + 姿态）并写 `observations.jsonl`，其余全在 Python**
（`examples/touch_eval/py/`，uv 工程）。C++ 的判定/评估实现与命令行工具已经删除，
离线精度评估的全部口径搬进了 `touch_eval` 包，并对拍冻结的参考产物（见 §0）。

```
标注（一触一行 CSV / 旧 .label）──┐
                                  ├─> GroundTruth ──┐
视频 ──aifootball_app──> observations.jsonl ─────────┼─> touch-eval ──> touch_report.json
                       （基模唯一产物）              │                 touch_events.jsonl
                                  └─> 判定/打分/渲染 ─┘
```

> 判定层本身（候选 → 阈值 → 迟滞 → 聚簇 → 极小值合并 → 门控 → 不应期）的逐步说明、
> 参数表与实测漏斗见 [`docs/touch_detection_logic.md`](../../docs/touch_detection_logic.md)；
> 汇报用的汇总（关键数字、参数表、实测明细、产物清单、每个数字的出处）见
> [`docs/touch_summary.md`](../../docs/touch_summary.md)。

## 0. Python 侧：业务逻辑与差分验证

C++ 只跑基模（检测 + 姿态）并写 `observations.jsonl`；**标注解析、触球判定、打分、报告与复查渲染
都在 Python**（`examples/touch_eval/py/`，uv 工程，包名 `touch_eval`，本仓库唯一的 Python 环境）。
C++ 的判定/评估实现（`src/`、`include/`、`main.cpp`、单测、`touch_eval_core`）与 app 的在线判定
（`TouchRuntime`、`TouchJsonlWriter`、渲染器的触球叠层、`--detect_touches` 等开关）**已经删除**：
app 现在只写 `observations.jsonl`，阈值只影响"怎么读观测"，不可能影响观测本身。

```bash
cd examples/touch_eval/py
uv sync                               # 建 .venv 并装 numpy / pillow（+ pytest）
uv sync --extra tools                 # 画图/烧视频的工具还要 matplotlib + opencv
uv run touch-eval --observations ../../../output/touch_eval_moving_pass/observations.jsonl \
                  --touches_csv ../../../data/移动传球.touches.csv \
                  --output_dir /tmp/py_run
uv run pytest -q                      # 单测 + 差分
```

产物与原来的 C++ 工具同名同结构（`touch_report.json` / `touch_events.jsonl`），参数也同名
（`--window_anchor end|centre|start`、`--point_window`、`--tolerance`、判定旋钮…），
`tools/*.py` 与 `run_touch_eval.sh` 已经全部改走 Python。

**差分口径**（`uv run pytest -q -m parity`，整段 16037 帧约 7 秒，当前 7/7 全绿）：

| 层 | 对拍对象 | 结果 |
| --- | --- | --- |
| 判定 | `touch_events.jsonl` 的 13 个字段 | **97/97 事件**逐字段一致（相对误差 < 1e-5，即 C++ 写文件的 6 位有效数字以内）|
| 判定 | 两个不应期 + 两个 gate 的计数 | 一致，事件总数一致 |
| 标注解析 | `--dump_gt` 的 JSON | **全字段一致**（97 touch / 3 no_touch / 6 low_quality / totals / 每条 warnings）|
| 打分 | `touch_report.json` | **全字段一致**：主口径、另一锚点视图、容差扫描、计数表 97 行、误检分解、诊断百分位、标定曲线、低质量第二视图、failures 的分组与计数、逐事件 `gt_index` + `verdict` |

参考产物**冻结在 `py/tests/reference/`**（`touch_report.json` / `touch_events.jsonl` /
`ground_truth.json`，C++ 删除前最后一次运行的输出），所以差分仍然是对着 C++ 在比，而不是
Python 和自己比；观测量太大（90 MB）留在 `output/`，可用 `TOUCH_EVAL_OBSERVATIONS` 指别处。
移植时有两处精度细节必须照搬：`speedWindowSec` 在 C++ 里是 **double**（其余几何参数是 `float`），
以及全部几何量走 **float32**（Python 侧用 `numpy.float32`）。性能：整段评估 **1.9 s**（读 89 MB JSONL 1.3 s）。

原因代号（也是文件名后缀）：

- FP `slot_taken`：落在标注窗口内，但该标注已被更近的检测配走；
- FP `adjacent`：贴着标注窗口（邻接半径 1.5 s 内），窗口里已无名额；
- FP `inside_no_touch`：落在标注者确认无触球的区间；
- FP `unannotated`：附近 1.5 s 内没有任何标注；
- FN `contact_but_no_event`：窗内球脚确实贴到阈值内，但事件被判太短或被合并；
- FN `never_near`：窗内球从未近到阈值；
- FN `no_ball` / `no_feet`：窗内没有可用球 / 没有可用脚点。

**整段播放视频的体积与速度**：这台机器上没有 ffmpeg CLI、OpenCV 也没有 H.264 编码器，只能出 mp4v，
整段 720p60 约 **400 MB**（有 ffmpeg 时自动改用 x264，约为其 1/5，由 `--playback-crf` 控制）。
要更小：`--stride 2`（写 30 fps，仍是实时）约减半，再 `--playback-width 960 --playback-height 540` 再减半；
`--max-frames N` 只渲染前 N 帧做预览。

旧的"按错误切片"短视频（`pr_errors.mp4` / `pr_errors_annotated.mp4`）**已停用删除**：逐条证据看那 88 张图，
整段看 `touch_playback.mp4`。它俩的半速 bug 也一并修了（60 fps 素材曾被写进 30 fps 容器、每段末尾还定格 1 s）：
现在按源帧率写、默认不定格（`--hold-frames` 可恢复定格，`--video` 可随时重出切片视频）。

工具会用"关掉两个不应期重跑一次"来判断漏检是不是被去重门控压掉的（表格里的"原始流"列）。

（`person 0` 那一列是"关掉同人任一脚去重"，它的 R 更高但 P 低——重复上报被算成误检了。）

### 1.4 精度路径：只有 fp16 一条

`config/moving_pass_720p.yaml` = fp16（`rf-detr-small-960-fp16-b8-fp32io.engine`），**整段 157.4 FPS / 6.35 ms
每帧**，是触球评估唯一维护的路径。

曾经有一条 TF32 孪生（只差一行 `enginePath`，`rf-detr-small-960-fp32tf32-b8.engine`），跑 57.5 FPS / 17.4 ms，
用来做"换精度路径会不会改变结论"的对照：结论是**不会** —— 触球主口径 0.546 vs 0.544、±30 帧 0.763 vs 0.759、
±10/±60/±120 帧的差在 ±0.03 内且方向不定，而吞吐差 **2.7 倍**。既然换路径不改变结论，孪生就不再维护
（配置与产物已删除），所有"当前结果"、差分测试与扫描曲线**只以 fp16 为准**。

引用速度或触球数字时写明走的是哪条即可（`enginePath` 写在 `app_run.log` 与 `observations.jsonl` 的 metadata 里）。

## 2. 判定算法

1. **单帧接触度量**：对每个 `state=observed` 的球（优先跟踪球 `track_id>=1`，没有它时用最近的候选）与每个
   人的**脚部关键点**（project-26 的 15..22：左右踝 + 大趾/小趾/脚跟，共 8 个）算
   `d = min ||ball_center - foot_point||`。
   - `virtual`（平滑插值）与 `predicted`（球外推）**一律不作为证据**。
   - 脚部关键点还需 `confidence >= keypointConfidence`（默认 0.2，与 `FootballTracker::BallSupportScore` 同口径）。
2. **阈值**：`tau = min( clamp(min(W,H) * contactDistanceRatio, minContactPx, maxContactPx),
   clamp(personHeight * personHeightRatio, minContactPx, maxContactPx) )`；720p 下人体尺度项通常被
   `minContactPx` 盖住，调灵敏度先调它。
3. **滞回**：进入 `d <= tau`（contact）、`d <= tau*releaseRatio`（band，簇继续保持）、其余（none，
   容忍 `maxGapFrames` 帧后结束簇）。
4. **事件**：簇内取**距离局部极小**那一帧作为事件时刻（`eventTimeMode 0`；换成"接触首帧/末帧/中点"都更差，
   见 §4 的负结果）；两个极小之间必须有 ≥ `minRiseFrames` 帧明显超出退出阈值、且相隔 ≥ `minSplitFrames`
   （默认 **24 帧 = 0.4 s**），才拆成两次触球（对应「同一秒 2 次」）；每个事件还要满足 `minContactFrames`
   帧接触，归属该帧最近脚点的人 `track_id` 与左/右脚。
5. **跨簇去重（不应期）**：两条规则，都是"后者丢弃"——
   - 同一人**同一脚**在 `refractoryFrames`（默认 **30 帧 = 0.5 s**）内再次报出：一次接触短暂越过退出阈值
     会被报两次；
   - 同一人**任意脚**在 `personRefractoryFrames`（默认 **30 帧**）内再次报出：球从两脚之间穿过、或者姿态
     把左右踝认反一帧时，同一次触球会被左右脚各报一次，而按"人+脚"做键的规则看不见它。标注本来就把
     这种情况写成一次触球（`both` 行 = 左右脚算一次），所以合并才是标注的意思。这条是本轮收益最大的一刀
     （默认路径上 ±30 帧 F1 0.735 → 0.763、参考路径 0.728 → 0.759，两条都召回不掉）。
6. 三个可选门控（**默认关闭**，因为它们在本数据上无增益，见 §4）：球速突变门控
   `minSpeedChangePxPerSec / minSpeedRatio`、只信被跟踪球 `requireTrackedBall`。它们的拒绝计数会
   写进报告（`events refused by the gates`），避免"悄悄吃掉召回"。

## 3. 指标怎么读

标注是粗的：`.label` 的一行只说明「这一秒里有一次触球」，还可能写「2 次」。把一行当成一个点、只给一个
匹配名额，等于拿标注的精度去罚检测器。所以报告分四层：

**① 主口径：计数感知（窗口 + 名额）**

- 一条标注 = 它代表的**窗口**。区间行（写了起止）= 它写的那段跨度；点行（只写一个时刻）由文件头的
  `point_window_sec` 与 `--window_anchor` 决定。**手写整秒的读法已经写进数据**：`00:29S` 一律展开成
  `28.00–29.00`（= `[S−1, S)`，由 `--expand_whole_seconds` 展开，该命令尚未移植，见 §5 的迁移缺口），
  所以当前这份 CSV 里**没有点行**，
  三种锚点给出同一组数字（0.546 / 0.546 / 0.546）；点行时代它们差 0.154（`end` 0.533 / `centre` 0.687 /
  `start` 0.544），来龙去脉与"7.62 算哪一行"的逐行例子见 §4.2。
  - 窗口一律**半开区间 `[from, to)`**：相邻两个窗口首尾相接而不是共享端点，所以"7.62 s 算哪一格"只有一个答案；
    正好压在边界上的事件（0.01 s 的标注会出现，例如 30.000 s 同时压在 `[29,30)` 与 `[30,31)` 上）只算一次。
- 一条标注发放 `count` 个名额（`(2次)` 给 2 个）；
- 预测事件落在窗口内且名额未用完才算命中；`TP=分配数`、`FN=Σcount−TP`、`FP=预测数−TP`。

**② 误检分类**（只做归因，不参与上面的 P/R）：把每个未命中事件按位置归类——

| 分类 | 含义 |
| --- | --- |
| same touch, another frame | 与某个已命中事件同人同脚、相距 `duplicateSec`(0.5 s) 内：同一次触球的另一帧 |
| same moment, window full | **落在某条标注窗口内，但这个窗口的名额已经用完**：那行只声明了一次触球，我们报了两/三次——不是"看错时刻"，而是"同一时刻报了多次" |
| inside a no_touch span | 落在标注者明确写了「这段无触球」的区间里（**唯一被确认的误检**） |
| next to an annotation | 距最近窗口 `adjacencySec`(1.5 s) 内但没落进去：标注分辨率/人眼误差造成 |
| unannotated | 附近没有任何标注：真正没人支持的检测 |

前两类合起来就是「同一时刻报多了」；报告末尾还会打印每个例子的**离窗口多少秒**，所以"差 0.1 秒"和"差 1.4 秒"能直接区分。

**③ 辅助口径：一对一事件级**（历史可比）：默认 `±10/30/60/120` **帧**（60 fps 下即 0.17/0.5/1/2 s）
容差下的**最优一配一**（最大基数匹配：先保证配对数量最多，再让最近的配对优先；贪心扫一遍会漏配，
例如「靠得近的检测同时够得着两条标注、另一条检测只够得着其中一条」时，贪心会把后一条吊死）。时间用帧说是因为标注就是照着帧号抄的（渲染视频顶栏烧录了 `frame=`），
报告里帧与秒并列打印；`--tolerance_frames 10,30` 换帧列表，`--tolerance 0.25,0.5` 用秒（会覆盖帧），
`--window_anchor end|centre|start` 换点标注窗口的锚点（见 §4.2），
以及按标注的「每秒次数」计数一致性。

**④ 漏检归因**：每条漏检落到「窗口内没球 / 球只有外推 / 没有可用脚点 / 球脚都近但被事件规则否掉 /
从没近到阈值」，并附窗口内最近距离与当时的阈值。

**⑤ 双口径：低质量行另算一份**

`low_quality_data=yes` 的行表示「这些帧太糊、人太小，标注者自己也判断不了」。报告同时给出两份分数：

- **全部标注**：按上面四层算；
- **剔除低质量**：把这些行删掉，并且把「只有这些行能解释」的预测一并从分子分母里去掉——它们既不算命中
  也不算误检，报告里给出被剔除的事件数，这样第二份分数不会因为偷偷缩小考题而虚高。

两份的差距就是「有多少分数压在不可判的帧上」。若文件没有任何行被标，报告会提示这一列的存在。

诊断区还会给：标注窗口内「有球/有可用球/有可用脚」的比例、标注时刻球-脚最近距离分位数 vs 全片背景分位数
（能不能分开，决定这项任务值不值得做）、球员框高度分布；低质量行的窗口也会单独统计（有球/有脚比例、
球员框高度、最近距离），用来回检"这一行标得对不对"。

`[t−0.25, t+0.75)` 0.646 → `[t, t+1)` 0.544。所以那个 0.154 的差不是检测的问题，是**标注写法**的问题——

**该不该把那 17 行 +1，是个可以单独决定的数据修改**：它不改任何检测行为，只改分母怎么理解；
要动的话留 `.bak`、我给出清单与前后对比。

## 5. 标注格式（v2：一触一行 CSV）

`data/移动传球.touches.csv`（**一行一次触球**，彻底消除"同一秒多次"的歧义）：

```csv
# point_window_sec: 1.00
# fps: 60.00
index,type,t_start_sec,t_end_sec,t_start_frame,t_end_frame,count,low_quality_data,ignore,note
1,touch,0.00,1.00,,,1,,,"整秒桶 00:01S = [0,1)"
2,touch,34.20,35.10,2052,2106,1,,,按帧钉死：帧 2052–2106
3,no_touch,12.00,15.00,,,0,,,keeper picks the ball up
4,touch,220.00,221.00,,,1,yes,,太模糊了人员
5,touch,47.00,47.00,,,1,,yes,这次标注我不认（时间抄错了）
```

（带帧号列时顺序是 `...,t_start_frame,t_end_frame,count,low_quality_data,ignore,note`；`ignore` 列可选，
老文件没有它也能解析。**`foot`/`player` 两列已从本仓库的 CSV 删除**——它们对判定与打分没有贡献
（`player` 全空，`foot` 只有 5 行有值），旧文件仍带这两列时照旧解析、只是不再使用。）

- **整秒写法一律展开成它代表的那一秒**：`00:01S` 写成 `0.00–1.00`（= `[S−1, S)`）。
  当前这份 CSV 已经展开过（每行的帧列也因此被清空：只有"写下来的帧"才留在文件里）；
  **自动展开的命令（原 `--expand_whole_seconds`）尚未移植到 Python**，要改新写的整秒行请手工展开
  或先补上这条命令（见本节末的迁移缺口）。
  这样做的好处是**文件自己说清了"整秒指哪一段"**：`--window_anchor` 只剩兼容意义，
  同一个检测在任何锚点下得到同一组数字（§4.2）。
- `t_end == t_start` 仍合法 = 一个**点**（没有展开的整秒、或你确实只写了一个时刻），
  它的窗口由文件头的 `point_window_sec` 与 `--window_anchor` 决定；`t_end > t_start` = 区间，
  窗口就是它写的这段跨度（半开 `[t_start, t_end)`，加 `--window_pad`）。
- 时间精确到 0.01 s：**渲染视频顶栏烧录了 `frame=` 与 `time=`**，暂停抄一下即可，不需要帧级标注工具。
- `type=no_touch` 是**负样本区间**（"这段时间没有触球"），是唯一能便宜地测 precision 的东西。
- `low_quality_data`：这一行太糊/人太小、**标注者也无法判断**（写 `yes/true/1/低质量/模糊` 生效，
  留空或写 `no/0/ok` 不生效）。它不改变你写的时间，只让评估**多出一份「剔除这些行」的分数**，
  见 §3 的 ⑤；5 行以内的实测影响见 §4。写错的取值会在报告里报出来（不会静默当否）。
- **`ignore`：这条标注我不认**（时间抄错了、这次其实不是触球、`(2次)` 拆分留下的空行……写
  `yes/true/1/ignore/exclude/忽略/无效` 生效）。与 `low_quality_data` 的区别：后者是"我看不清，两边都算一份"，
  前者是"这条不算数"——**所有口径都不计它**（容量、召回、误检分类、双口径），报告开头会写明
  `N ignored row(s) (not scored anywhere)`，`touch_report.json` 的 `ignored` 段也会逐条列出。
  行**保留在文件里**（带 `ignore=yes`），`--renumber_touches`、`--dump_gt`、`--dump_gt_csv` 都不会丢它，
  后悔了把 `yes` 删掉即可。想真正删掉某行就直接删那一行（不可逆，两种都行）。
- 文件头的 `# point_window_sec:` 只对**还留在文件里的点行**有效（手写 0.01 s 的瞬时值默认 0.5，
  从 `.label` 整秒转来的用 1.0，`--point_window` 可覆盖）；整秒行展开成区间之后这份文件里没有点行了，
  这一行只是留给 `.label`/新文件的默认值。
- 列名可换（`start/end/count/low_quality_data/note`、`开始/结束/次数/备注` 都认；
  `foot`/`player` 两个列名仍被识别，但已不再使用，见上），
  无表头时按"老 8 列"顺序解析（`low_quality_data` 需要表头）。
- `index` 列**会被采纳**：报告里的 `gt#N` 就是你文件里的这一列，手改出重号时后面的行自动顺延并在
  该行的 `warnings` 里说明。写完想重排一遍：

  （原 `--renumber_touches` 会原地重写：序号 1..N + 补齐规范列 + 留 `.bak`；**该命令尚未移植**，
  当前文件已经重排过。）
- **帧号可选，且优先级高于秒**（用来把一帧钉死、又不用重算时间）：

  ```csv
  # fps: 60
  index,type,t_start_sec,t_end_sec,t_start_frame,t_end_frame,count,low_quality_data,note
  4,touch,266.83,266.83,16010,16010,1,,confirmed by frame
  ```
  `frame`（单列）同时设首尾；**声明了 fps 才能用帧号**，否则该列会被"报告并忽略"而不是被瞎猜
  （报告会在 `ground truth warnings` 里说明"帧列被忽略"，不会静默）；
  `--fps 60` 可以覆盖/补上文件里没写的帧率。
  - **帧号是闭区间**：`419–440` 表示 419 和 440 都是这次触球覆盖的帧，所以它代表的区间是
    `[419/60, 441/60)` —— 不这样解释的话"末帧"会掉在自己的窗口外面。
  - **只有写下来的帧才会被写回文件**：从秒推出来的帧（只给秒、文件又声明了 fps 时工具会自动补）
    不在其中，所以写文件的命令不会把推出来的帧写进你的文件、也不会在下次读取时反过来覆盖你的秒；
    整秒展开清空的正是这种推出来的帧。
  - 写成区间的行，窗口就**只有这段跨度**，不再额外给 1 s——所以"只知道大概一秒"的行请写整秒
    （再展开成 `[S−1,S)`），别写成十几帧的区间，否则那一条会突然变严。

> ⚠️ 写 CSV 的命令（原 `--dump_gt_csv` / `--renumber_touches`）会**覆盖**目标文件：别把它们指向你
> 手改过的 `data/移动传球.touches.csv`。这两条命令**都还没移植到 Python**，见下面的迁移缺口。

**旧 `.label` 继续支持**，两者归一到同一个真值结构。把 `.label` 转成 v2：

**注意：`.label` 已经能直接评估**（`uv run touch-eval --label ...` 会自动按扩展名选择解析器，

## 7. 已知限制

- **标注的分辨率是现在的天花板**：97 条标注里 **14 条在 ±0.5 s 内完全没有预测**（最近的差 0.53~2.58 s），
  所以一对一召回上限是 **76.3 %**；剩下 33 个"贴着跨度"的误检都落在跨度外 0.07~1.48 s 处，而其中 64 条
  标注只写了 1 s 宽。两边都是"时刻差 0.2 秒"级别的判定分歧，**参数调不动它**：要判断谁对，只能把那十几条
  标注钉到帧上（渲染视频顶栏有帧号，抄一帧和抄一秒的成本一样）。
- 反过来，如果目标是"更宽松但同样可信"的口径：±60 帧是 0.814，±120 帧是 0.887，过程级（同人同脚
  1 s 内合并成一次触球）是 0.585/0.546——引用时写清楚用了哪一个。
- **辅助 ±T 一对一不再是"时刻准不准"的度量**（§4.1）：所有行都写成区间之后，事件落在跨度内就按 Δt=0 计，
  ±10 帧那一列因此从 0.410 涨到 0.608。它现在回答"这次触球有没有独立的标注可配"。
- **"一个整秒指哪一秒"现在由数据承担**（§4.2）：整秒行都已展开成 `[S−1, S)`，所以锚点不再是变数。
  历史账留着：点行时代三种读法差 0.154（`end` 0.533 / `centre` 0.687 / `start` 0.544），而数据更像
  `centre`（25 行抄准的整秒里只有 8 行落在 `[S−1, S)`）。**要不要把那 17 行"写早了一秒"的秒号 +1，
  是一个还没做的数据修改**——它不改检测行为，只改分母怎么理解。
- **±0.5 s 的限制来自标注分辨率，不是检测**：14 条标注在 ±0.5 s 内没有任何预测（最近差 0.53~2.58 s），
  其中 2 条（48.00–49.00 s / 91.00–92.00 s）窗内球离最近脚点还有 118 / 260 px，可能是非脚触球（头/手/胸）
  或时刻写偏。详见 §4.1 的天花板分析（一对一口径 0.763，绝对上限 0.865）。
- `no_touch` 区间只有 3 段，precision 的分母仍然很薄；「无人支持」的判定依赖 `adjacencySec`(1.5 s) 这个
  人为半径。
- 主口径的容量来自你写的行数：少写一行 = recall 的分子分母同时少一块，**它无法发现"标注漏了"**。
  126.73 s / 131.62 s 那两个预测就是例子（§4），只能靠人复核。
- 脚别核对（`foot hint`）**没有实做**：v2 CSV 的 `foot`/`player` 两列已删除，只有 legacy `.label`
  的脚别文字仍在（`左脚/右脚/左右脚`），报告里也不输出这一项。
- 只有一条视频的标注；阈值、不应期都是从它标定出来的，换场景请重跑曲线与消融。
- 只判「脚触球」（踝/趾/跟）；头/手/胸触球未纳入。
- 判定依赖「球被检出且脚部关键点可见」；报告的漏检归因会说明卡在哪一环。
